# 프롬프트 3기법 비교 리포트

- 실행 환경: ChatGPT 무료 웹 UI, 21회 모두 새 채팅에서 실행
- 첨부: `captures/`에 캡처 21장, `prompts.txt`·`prompts_filled.txt`에 프롬프트 원본, `results.txt`에 출력 원문, `format_check.py`로 형식 판정

---

## 1. 과업 정의

- **선택:** (가) 고객 문의 분류 + 긴급도
- **분류 항목:** 주문 / 배송 / 환불 / 제품문의 / 기타

| 항목 | 범위 |
|---|---|
| 주문 | 결제, 주문 내역, 주문 변경 |
| 배송 | 배송 상태, 배송 조회, 배송지 |
| 환불 | 환불, 반품, 교환 |
| 제품문의 | 제품 스펙, 호환성, 사용법, 재입고 |
| 기타 | 회원, 포인트, 쿠폰, 영수증 등 |

- **경계 판정 규칙:** 견본 `inquiries_labeled.csv`의 애매 사례(Q16~Q20) 라벨에서 도출했다.
  1. 원인이 아니라 고객이 **최종적으로 원하는 것**으로 분류한다. (Q16 파손→환불, Q18 배송 지연→환불)
  2. 요청이 **조건부**("~하면 ~해 주세요")이면 **현재 사안**으로 분류한다. (Q19·Q20 → 제품문의)

- **긴급도 기준:** 견본 라벨에서 도출했다.

| 긴급도 | 기준 | 견본 근거 |
|---|---|---|
| 3 | 금전 피해가 진행 중이거나, 시간 제한이 있거나, 강한 긴급 표현과 피해가 함께 있음 | Q11 이중결제, Q02 "오늘까지", Q12 출고 전 주소 정정 |
| 2 | 문제가 발생해 처리가 필요하지만 시간 제한은 없음 | Q01, Q07, Q08, Q15 |
| 1 | 문제가 발생하지 않은 단순 정보·정책 문의 | Q03, Q04, Q09, Q13 |

- **출력 형식:** `{"type": "분류항목", "urgency": 숫자}`
- **형식 준수(O/X) 판정 기준:** 출력 전체(Zero-shot, Few-shot) 또는 약속한 마지막 줄(CoT)을 `json.loads()`로 그대로 읽을 수 있으면 O. 판정은 `format_check.py`로 자동 수행했다.

## 2. 테스트 입력과 내 정답 (실행 전 작성)

| # | 입력 문장 | 명확/애매 | 내 정답 (유형/긴급도) | 애매하다고 본 이유 |
|---|---|---|---|---|
| 1 | 배송조회는 어디서 할 수 있나요? | 명확 | 배송 / 1 | – |
| 2 | 배송지 주소를 변경하고 싶어요 배송되기 전에 빨리 주소지를 바꿔주세요 | 명확 | 배송 / 3 | – |
| 3 | 사이즈가 안맞아서 사이즈를 교환하고 싶어요 | 명확 | 환불 / 2 | – |
| 4 | 반품하고 싶은데 상자가 좀 훼손되게 뜯었는데 반품 가능한가요 | 애매 | 환불 / 1 | "반품하고 싶은데"는 **요청**처럼 보이지만 문장의 실제 질문은 "가능한가요"라는 **정책 문의**다. 유형(환불 vs 제품문의·기타)과 긴급도(문제가 이미 생긴 것으로 보면 2, 단순 문의로 보면 1)가 갈린다. |
| 5 | 배송이 아직도 안 와요. 계속 안 오면 그냥 환불받고 싶어요 | 애매 | 배송 / 2 | "환불"이라는 단어가 있어 환불로 분류하기 쉽지만, 환불은 **조건부**이고 현재 사안은 배송 지연이다. |

- PII 점검: 다섯 문장 모두 실명, 연락처, 주소, 주문번호 등 개인 식별 정보를 포함하지 않는다.
- 문장 1~4는 직접 작성했다. 문장 5는 처음에 쓴 문장이 견본 Q18과 거의 같아서 조건부 요청으로 고쳤다(8장 참고).

## 3. 프롬프트 전문

세 프롬프트는 **역할, 분류 항목, 경계 규칙, 긴급도 기준, 출력 형식을 똑같이** 두고 기법 부분만 다르게 했다. 결과 차이가 기법에서 나왔다고 말할 수 있게 하기 위해서다.

### Zero-shot

```
당신은 온라인 쇼핑몰 고객센터의 문의 분류 담당자입니다.
아래 고객 문의를 분류하고 긴급도를 판정하세요.

[분류 항목] 주문 / 배송 / 환불 / 제품문의 / 기타 중 하나
- 주문: 결제, 주문 내역, 주문 변경
- 배송: 배송 상태, 배송 조회, 배송지
- 환불: 환불, 반품, 교환
- 제품문의: 제품 스펙, 호환성, 사용법, 재입고
- 기타: 회원, 포인트, 쿠폰, 영수증 등
- 원인이 아니라 고객이 최종적으로 원하는 것을 기준으로 분류한다.
- 요청이 조건부("~하면 ~해 주세요")이면 현재 사안을 기준으로 분류한다.

[긴급도]
- 3: 금전 피해가 진행 중이거나, 시간 제한이 있거나, 강한 긴급 표현과 피해가 함께 있음
- 2: 문제가 발생해 처리가 필요하지만 시간 제한은 없음
- 1: 문제가 발생하지 않은 단순 정보·정책 문의

[출력 규칙]
JSON 한 줄만 출력하세요. 설명, 인사말, 코드블록(```)은 쓰지 마세요.
형식: {"type": "분류항목", "urgency": 숫자}

문의: {테스트 문장}
```

### Few-shot

Zero-shot 프롬프트의 `[출력 규칙]` 뒤에 아래 예시 5개를 추가했다. 예시는 견본에서 골랐고, **5개 유형을 하나씩, 긴급도 1·2·3을 모두** 포함하도록 했다. 경계 규칙을 보여 주는 사례(Q16 원인≠요청, Q20 조건부)를 넣었고, 테스트 5건과 겹치는 문장은 없다.

```
(Zero-shot과 동일한 역할·분류 항목·긴급도·출력 규칙)

[예시]
문의: 결제가 두 번 됐어요! 카드값 이중청구된 것 같아요. 급합니다.
출력: {"type": "주문", "urgency": 3}

문의: 송장번호가 조회가 안 돼요. 배송 어디쯤인지 알 수 있을까요?
출력: {"type": "배송", "urgency": 2}

문의: 상품이 파손돼서 왔어요. 당장 환불해 주세요, 급합니다!
출력: {"type": "환불", "urgency": 3}

문의: 언제쯤 재입고되나요? 안 되면 환불 문의도 하려고요.
출력: {"type": "제품문의", "urgency": 1}

문의: 회원 탈퇴는 어디서 하나요?
출력: {"type": "기타", "urgency": 1}

문의: {테스트 문장}
출력:
```

### CoT

Zero-shot 프롬프트에 **추론 단계 4개를 직접 지정**하고, 출력 규칙을 "추론 먼저, 마지막 줄은 JSON만"으로 바꿨다.

```
(Zero-shot과 동일한 역할·분류 항목·긴급도)

[추론 단계] 다음 순서대로 한 줄씩 추론하세요.
1단계: 고객이 최종적으로 원하는 것은? (요청인지, 단순 질문인지)
2단계: 그 요청이 지금 바로 원하는 것인지, 조건부인지 확인
3단계: 1~2단계에 맞는 분류 항목 결정
4단계: 이미 문제가 발생했는지, 금전 피해나 시간 제한이 있는지 확인 → 긴급도 결정

[출력 규칙]
추론을 먼저 쓰고, 마지막 줄에는 JSON 한 줄만 쓰세요.
마지막 줄에는 JSON 외에 어떤 글자도, 코드블록(```)도 쓰지 마세요.
형식: {"type": "분류항목", "urgency": 숫자}

문의: {테스트 문장}
```

세 프롬프트의 전체 원문은 `prompts.txt`에, 실제로 붙여 넣은 15개 완성본은 `prompts_filled.txt`에 있다.

## 4. 결과 표 (15회)

| # | 내 정답 | Zero-shot 결과 | Few-shot 결과 | CoT 결과 (마지막 줄) |
|---|---|---|---|---|
| 1 | 배송/1 | `{"type": "배송", "urgency": 1}` 형식 O / 정답 O | `{"type": "배송", "urgency": 1}` 형식 O / 정답 O | `{"type": "배송", "urgency": 1}` 형식 O / 정답 O |
| 2 | 배송/3 | `{"type":"배송","urgency":3}` 형식 O / 정답 O | `{"type": "배송", "urgency": 3}` 형식 O / 정답 O | `{"type": "배송", "urgency": 3}` 형식 O / 정답 O |
| 3 | 환불/2 | `{"type":"환불","urgency":2}` 형식 O / 정답 O | `{"type": "환불", "urgency": 2}` 형식 O / 정답 O | `{"type": "환불", "urgency": 2}` 형식 O / 정답 O |
| 4 (애매) | 환불/1 | `{"type": "환불", "urgency": 1}` 형식 O / 정답 O | `{"type": "환불", "urgency": 1}` 형식 O / 정답 O | `{"type": "환불", "urgency": 2}` 형식 O / **정답 X** (긴급도) |
| 5 (애매) | 배송/2 | `{"type":"배송","urgency":2}` 형식 O / 정답 O | `{"type": "배송", "urgency": 2}` 형식 O / 정답 O | `{"type": "배송", "urgency": 2}` 형식 O / 정답 O |
| **합계** | | 형식 5/5, 정답 5/5 | 형식 5/5, 정답 5/5 | 형식 5/5, 정답 **4/5** |

- CoT 출력은 추론 문장과 JSON이 함께 있어서 **출력 전체를 `json.loads()`에 넣으면 5건 모두 실패**한다. 약속대로 마지막 줄만 꺼내면 5건 모두 성공하므로 형식 O로 판정했다.
- CoT case 4 1회차 추론 원문:
  > 2단계: 현재 반품을 원하는 상황이지만, 반품 가능 여부를 묻는 **단순 정책 문의이다.**
  > 4단계: 반품 관련 **문제가 발생했지만** 금전 피해 진행이나 시간 제한은 없으므로 긴급도는 2이다.

  2단계에서 "단순 정책 문의"라고 판단해 놓고 4단계에서 "문제가 발생했다"고 판단해, **추론이 스스로 모순**된다.

## 5. 반복 실행 (애매 사례 #4, 기법별 3회)

15회 중 기법 간 답이 갈린 사례가 #4뿐이어서 #4를 반복 대상으로 골랐다. 1회 = 4장의 본 실행 결과이고, 2·3회는 각각 새 채팅에서 같은 프롬프트로 실행했다.

| 기법 | 1회 | 2회 | 3회 | 같은 답이었나 |
|---|---|---|---|---|
| Zero-shot | 환불/1 (O) | 환불/1 (O) | 환불/1 (O) | 3/3 동일 |
| Few-shot | 환불/1 (O) | 환불/1 (O) | 환불/1 (O) | 3/3 동일 |
| CoT | 환불/**2** (X) | 환불/1 (O) | 환불/1 (O) | **2/3** (1회만 긴급도 다름) |

- 6회 모두 형식 O.
- CoT 2·3회차는 4단계에서 "금전 피해가 진행 중이거나 시간 제한이 있다는 언급은 없으므로 1", "아직 반품 거부나 금전 피해가 발생하지 않았고…1"로 정확히 판단했다. 같은 프롬프트에서도 **추론 경로가 매번 달라지고, 그에 따라 결론도 흔들렸다.**

## 6. 분석

### 형식 준수

- 세 기법 모두 21회 중 형식 위반이 없었다 (Zero-shot 7/7, Few-shot 7/7, CoT 7/7).
- Zero-shot은 공백 표기가 실행마다 달랐다(`{"type":"배송","urgency":3}` vs `{"type": "배송", "urgency": 1}`). 파싱에는 영향이 없지만 **출력 모양이 고정되지 않았다**는 뜻이다. Few-shot은 7회 모두 예시와 똑같은 표기(`{"type": "...", "urgency": n}`)를 따랐다. 강의에서 말한 "예시가 출력 형식을 고정한다"는 효과가 공백 수준에서 관찰되었다.
- CoT는 마지막 줄 약속을 지켰지만, 마지막 줄 앞에 빈 줄이 있는 경우(case 2·3·5)와 없는 경우(case 1·4)가 섞여 있었다. 실제 파이프라인에서는 "마지막 **비어 있지 않은** 줄"을 꺼내도록 구현해야 안전하다. 출력 전체를 그대로 `json.loads()`에 넣으면 7회 모두 실패하므로, **CoT는 파싱 규칙을 별도로 약속하고 코드에서 지켜야만 쓸 수 있는 기법**이다.

### 분류 정확성

- 명확 사례(#1~#3): 세 기법 모두 9/9 정답이었다. 명확한 문장에서는 기법 차이가 없었다.
- 애매 사례(#5 조건부 환불): 세 기법 모두 정답(배송/2)이었다. 프롬프트에 넣은 **"조건부 요청은 현재 사안 기준"** 규칙이 Zero-shot에서도 제대로 작동했다. 규칙을 명시하면 Zero-shot만으로도 경계 사례를 처리할 수 있다는 근거다.
- 애매 사례(#4 요청 vs 정책 문의): 유형(환불)은 21회 모두 맞혔다. 차이는 **긴급도**에서만 났다. CoT 1회차가 "문제 발생 여부"를 잘못 판단해 2를 줬다. CoT의 장점인 "단계별 판단"이 이번에는 오히려 **중간 단계에서 잘못된 판단을 만들어 결론을 틀리게 하는 경로**가 되었다.
- 전체 정답률(21회 기준): Zero-shot 7/7, Few-shot 7/7, CoT 6/7.

### 일관성

- Zero-shot과 Few-shot은 반복 3회에서 3/3 동일, CoT는 2/3이었다.
- CoT는 추론 문장을 길게 생성하는 과정에서 매번 다른 표현과 다른 판단 경로가 나온다. 판단 단계가 많을수록 **흔들릴 지점도 많아진다.** 이번 실험에서 유일한 불일치가 CoT에서 나온 것은 이와 맞는다.
- 다만 반복 횟수가 기법당 3회뿐이라, "CoT가 더 불안정하다"를 통계적으로 단정할 수는 없다.

### 비용

출력 길이(문자 수, `format_check.py`로 측정)를 비교했다.

| 기법 | 평균 출력 길이 | Zero-shot 대비 | 프롬프트(입력) 길이 |
|---|---|---|---|
| Zero-shot | 약 27자 | 1배 | 523자 |
| Few-shot | 28자 | 1배 | 873자 (예시 5개 추가) |
| CoT | 약 225자 | **약 8배** | 731자 (추론 단계 추가) |

- Few-shot은 **입력** 토큰이 약 1.7배로 늘지만 출력은 그대로다.
- CoT는 **출력** 토큰이 약 8배로 늘어난다. 일반적으로 출력 토큰 단가가 입력보다 비싸므로 대량 처리(예: 리뷰 수천 건)에서는 비용 차이가 더 커진다.
- 이번 실험에서는 CoT가 정확성과 일관성 어느 쪽도 높이지 못했으므로, **추가 비용을 들일 근거가 없었다.**

### 한계

- 테스트가 5건, 반복이 3회로 표본이 작다.
- 세 프롬프트 모두에 경계 규칙을 자세히 넣었기 때문에 Zero-shot도 정답률이 높았다(천장 효과). 규칙 없는 Zero-shot과 비교했다면 기법 간 차이가 더 크게 나왔을 수 있다.
- 정답 유형이 배송·환불에만 분포해서 주문·제품문의·기타 사례는 검증하지 못했다.
- 무료 ChatGPT는 사용량에 따라 응답 모델이 바뀔 수 있어 실행 간 조건이 완전히 같다고 보장할 수 없다.

## 7. 결론 — 우리 팀이 쓸 기본 전략

**기본 전략: "명시적 경계 규칙 + Few-shot"**

1. **Few-shot을 기본으로 쓴다.**
   - 21회 기준 정답 7/7, 반복 3/3 일관, 형식 7/7로 가장 안정적이었다.
   - 출력 표기까지 예시와 똑같이 고정되어 파싱 코드가 단순해진다.
   - 늘어나는 비용은 입력 토큰(예시)뿐이고, 출력 길이는 Zero-shot과 같다.
2. **경계 규칙은 반드시 프롬프트에 문장으로 명시한다.**
   - "원인이 아니라 최종 요청", "조건부면 현재 사안" 규칙 덕분에 애매 사례 #5를 모든 기법이 맞혔다. 성능을 가장 크게 좌우한 건 기법보다 **규칙의 명시**였다.
   - Few-shot 예시에도 경계 사례를 1~2개 넣어 규칙을 보여 준다.
3. **CoT는 기본값으로 쓰지 않고, 제한적으로만 쓴다.**
   - 출력 비용이 약 8배인데, 이번 과업에서는 정확성과 일관성 모두 개선이 없었고 오히려 유일한 오답과 불일치가 CoT에서 나왔다.
   - 정책 판단이나 계산처럼 **조건이 여러 개 얽힌 과업**, 또는 판정 근거를 사람이 검토해야 하는 경우에만 쓴다.
   - 쓸 때는 추론을 JSON 안의 `"reason"` 칸에 담게 하거나, "마지막 비어 있지 않은 줄"만 파싱하도록 코드에서 처리한다.
4. **코드 쪽 방어를 함께 둔다.** 기법과 무관하게 `json.loads()` 실패를 잡아 실패 건수를 집계한다(과제 2와 연결). 이번 21회에서는 형식 위반이 없었지만, 실제 대량 처리에서는 코드펜스나 사족이 섞인 응답이 나올 수 있다.
