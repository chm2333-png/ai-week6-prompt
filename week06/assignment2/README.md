# 과제 2 — Mock 분류기 확장 (불량 응답 주입과 실패 집계)

LLM은 가끔 형식이 깨진 답을 준다. `mock_llm_call`이 20% 확률로 불량 응답을 내도록 만들고, 파이프라인이 그런 답을 만나도 멈추지 않으면서 **실패를 세어서 보고**하도록 확장했다.

## 1단계: 불량 응답 만들기 (`mock_llm.py`)

```python
MALFORMED_RATE = 0.2
MALFORMED_TYPES = ["codefence", "chatter", "truncated"]

if random.random() < MALFORMED_RATE:            # 20% 확률로 불량 응답
    malformed = random.choice(MALFORMED_TYPES)   # 세 유형 중 무작위 1개
    text = _make_malformed(canned, malformed)
```

| 유형 | 실제 응답 예시 |
|---|---|
| 코드펜스형 | ` ```json\n{"category": "배송", "sentiment": "긍정", "score": 4}\n``` ` |
| 사족형 | `물론입니다! 분석 결과는 다음과 같습니다. {"category": "배송", ...}` |
| 잘린 JSON형 | `{"category": "배송", "` (무작위 위치에서 잘림, `stop_reason="max_tokens"`) |

- 잘린 JSON은 실제 API처럼 `stop_reason`을 `"max_tokens"`로 바꿔 돌려준다. 강의노트 3.3절에서 말한 "stop_reason 확인!"을 흉내 낸 것이다.
- 유형별 복구율을 세려면 어떤 불량이 주입됐는지 알아야 한다. 그래서 응답에 **테스트 전용 필드 `_malformed`**를 붙였다. 실제 API 응답에는 없는 필드이므로 13주차에 실제 호출로 교체할 때 함께 제거한다.

## 2단계: 실패 집계 (`classify.py`, `run_pipeline.py`)

`classify_review`는 강의노트 3.3절의 3중 방어를 그대로 유지하고, 결과를 추적하는 `trace` 딕셔너리만 추가했다.

| 방어 | 하는 일 | 걸러내는 불량 |
|---|---|---|
| 방어 1 | ` ``` `로 시작하면 백틱과 `json` 표기를 걷어냄 | 코드펜스형 → **복구** |
| 방어 2 | `json.loads()` 실패 시 `None` 반환 | 사족형, 잘린 JSON형 → **실패** |
| 방어 3 | `category`가 허용 목록에 없으면 `None` 반환 | (이번 실행에서는 해당 없음) |

집계 루프는 `None`을 받으면 **건너뛰되 반드시 센다.**

```python
for review in reviews:
    result = classify_review(review, trace=trace)
    if trace["malformed"]:
        injected[trace["malformed"]] += 1
        if result is not None:
            recovered[trace["malformed"]] += 1
    if result is None:   # 조용히 버리지 않고 센다
        failed += 1
        continue
    stats[result["category"]] += 1
```

## 3단계: 실행 결과 (`reviews_sample.csv` 200건, seed=42)

실행 화면 캡처: [captures/](captures/) · 출력 원문: [captures/run_output.txt](captures/run_output.txt)

```
처리 200건 / 실패 31건  (성공 169건, 성공률 84.5%)

[불량 응답 유형별 결과]  불량 응답 50건 (25.0%) 중 복구 19건, 실패 31건
  유형          발생  복구  실패
  코드펜스형    19    19    0
  사족형        17    0     17
  잘린 JSON형   14    0     14
  합계          50    19    31
```

### 실패 M건이 불량 응답 건수보다 적은 이유

불량 응답은 50건이었는데 실패는 31건이다. 차이 19건은 **코드펜스형 19건 전부를 방어 1이 걷어내 정상 처리했기 때문**이다. 코드펜스형은 형식만 어긋났을 뿐 안에 온전한 JSON이 있어서, 백틱과 `json` 표기만 지우면 `json.loads()`가 성공한다. 반면 사족형(17건)과 잘린 JSON형(14건)은 방어 1의 조건(` ``` `로 시작)에 걸리지 않고 방어 2에서 `None`이 되어 모두 실패했다.

> 실패 31건 = 불량 50건 − 코드펜스형 복구 19건 = 사족형 17건 + 잘린 JSON형 14건

### 관찰: 실패를 세지 않으면 집계가 조용히 왜곡된다

실패 31건은 카테고리 집계에서 통째로 빠진다. 기본 방어의 집계는 `{'기타': 110, '배송': 39, '품질': 17, '환불': 3}`(합계 169)인데, 정규식으로 실패를 줄이면 `{'기타': 123, '배송': 41, '품질': 18, '환불': 4}`(합계 186)가 된다. "처리 N건 / 실패 M건"을 같이 출력하지 않으면, 보고서를 읽는 사람은 **200건 중 169건만 집계된 숫자**라는 걸 알 수 없다. 이게 "건너뛴 건을 조용히 버리지 말고 세어서 보고하라"는 요구의 이유다.

### 참고: 불량 비율이 20%가 아니라 25%인 이유

seed=42에서는 200건 중 50건(25%)이 불량으로 뽑혔다. 각 호출이 독립적으로 20% 확률로 불량이 되므로, 200건이면 평균 40건이고 실행마다 위아래로 흔들린다. 다른 시드로 돌려 보면 아래처럼 35~50건 사이에서 움직인다.

| seed | 불량 응답 | 기본 방어 실패 | 정규식 복구 실패 |
|---|---|---|---|
| 1 | 35 | 15 | 7 |
| 2 | 36 | 24 | 15 |
| 3 | 40 | 32 | 19 |
| 4 | 38 | 27 | 12 |
| 5 | 40 | 24 | 9 |
| 42 | 50 | 31 | 14 |
| 100 | 46 | 31 | 15 |

모든 시드에서 **"실패 = 사족형 + 잘린 JSON형"** 관계가 그대로 성립했다.

## 도전 과제: 정규식으로 사족형 복구

방어 2에서 `json.loads()`가 실패하면 응답 안에서 `{`부터 `}`까지를 정규식으로 골라내 한 번 더 파싱한다 (`classify_review(..., rescue=True)`).

```python
JSON_BLOCK = re.compile(r"\{.*\}", re.DOTALL)

def _rescue_json(raw):
    match = JSON_BLOCK.search(raw)
    if match is None:
        return None
    try:
        return json.loads(match.group(0))
    except json.JSONDecodeError:
        return None
```

같은 시드(42)로 두 방식을 실행해 비교했다. 같은 시드로 시작하므로 두 실행은 **완전히 같은 불량 응답**을 받는다.

| 유형 | 발생 | 기본 방어 복구 | 정규식 추가 복구 |
|---|---|---|---|
| 코드펜스형 | 19 | 19 | 19 |
| 사족형 | 17 | 0 | **17** |
| 잘린 JSON형 | 14 | 0 | 0 |
| **실패 합계** | | **31건** | **14건 (17건 감소, 약 55% 감소)** |

성공률은 84.5% → 93.0%로 올랐다.

### 잘린 JSON은 왜 여전히 복구할 수 없는가

1. **정규식이 매치될 대상이 없다.** 잘린 응답(예: `{"category": "배송", "`)에는 닫는 `}`가 없다. `\{.*\}`는 `{`와 `}`가 둘 다 있어야 매치되므로 아예 아무것도 찾지 못한다.
2. **정보 자체가 사라졌다.** 사족형은 앞에 군더더기가 붙었을 뿐 JSON이 **온전히 들어 있어서** 잘라내기만 하면 된다. 잘린 JSON은 뒤쪽의 `sentiment`, `score` 값이 응답에 **애초에 존재하지 않는다.** 괄호를 억지로 닫아도 빠진 값은 만들어 낼 수 없고, 추측해서 채우면 틀린 데이터가 조용히 섞인다.
3. **올바른 대응은 파싱이 아니라 재요청이다.** 잘림은 `stop_reason == "max_tokens"`로 미리 알 수 있다. 이때는 `max_tokens`를 늘려 다시 호출하거나 실패로 기록해야 한다. 13주차 실제 API 연동에서 재시도 로직으로 확장할 부분이다.

### 정규식 복구의 위험

`\{.*\}`는 탐욕적(greedy) 매치라 첫 `{`부터 **마지막** `}`까지 잡는다. 사족 안에 `{`나 `}`가 또 있거나 JSON 객체가 두 개 나오면 엉뚱한 구간을 잡을 수 있다. 그래서 복구한 결과도 반드시 방어 3(카테고리 검증)을 다시 통과하도록 했다. 정규식 복구는 기본값을 끄고(`rescue=False`) 필요할 때만 켜도록 두었다.
